AutoSkill · Deep Dive 07

Evaluating Skills, Not Just Agents: Agentic Continuous Evaluation of Skills

Every gate in the skills ecosystem reads the document. ACES runs it, twice — once with the skill and once without — and reports the difference. The headline is that the difference is large. The finding this project has to sit with is that nothing you can read off the document predicts it.

01

Compiling clean is not running correctly

The paper opens with an analogy that is worth taking literally, because the entire contribution follows from it. Running a skill through the evaluation tools that exist today, the authors say, is like compiling a program with -Wall -Werror: the absence of warnings does not mean the program does what it should. Every gate currently deployed in the skills ecosystem — structural checkers, rubric judges, linters, security scanners — shares one structural property. They read the skill document. None of them runs it.

That would be a pedantic observation if the failures it predicts were rare or exotic. They are neither. The authors enumerate five ways a skill can scan perfectly and still fail at runtime, and each one is a failure of a different link in the chain between a document and a completed task. The agent may never discover the skill when the user asks a relevant question. It may read the documentation and then invoke the wrong script, or the right script with the wrong arguments. It may produce correct output and then misinterpret and misreport it. It may collide with another skill already sitting in the same workspace. Or it may be silently regressed by a model update that changes how the agent reasons about documentation that nobody touched. None of these is visible in the skill alone, because none of them is a property of the skill alone — each is a property of the skill in a particular workspace, under a particular model, on a particular task.

The paper's response is ACES, which stands for Agentic Continuous Evaluation of Skills: a framework that runs a live agent on the skill author's own tasks under two conditions, one where the target skill is available and one where it is withheld, and reports the difference. That difference is the paper's headline quantity, Skill Lift. Everything else in the system — the trace format, the container staging, the six-metric evaluator suite, the decoy skills — exists to make that difference measurable, comparable across agent harnesses, and cheap enough to run on every merge request.

Before any of that machinery arrives, though, the authors do something more useful than proposing it. They measure how badly the existing gates need replacing, and the measurement turns out to be the most quotable result in the paper.

02

What the four scanning classes actually measure

The four scanning classes are worth spelling out rather than name-dropping, because they are almost exactly what this project plans to build as its own cheap pre-filter, and because each one fails at the deployment question in a different way.

Structural checking is the cheapest tier: roughly fifty deterministic rules, no API key, milliseconds per skill, safe to put in a blocking gate. The rules are grouped into four weighted dimensions, each of which starts at 100 and takes a severity-weighted deduction on every finding. Correctness carries the most weight at 0.35 and covers the frontmatter contract (does the skill declare name, description, version, author, tags, tools), whether the directory name matches the declared name, whether an Instructions section exists, whether declared scripts are actually present, and whether the text contains characters that look like prompt injection. Discoverability at 0.25 is about whether the agent will ever find the skill: description length, with 50 to 150 characters preferred and anything over 200 flagged as overlong, the presence of trigger vocabulary like "use", "when" and "for", explicit negative and boundary phrasing, and whether the skill says when to use it. Reliability, also 0.25, looks for error-handling vocabulary, input-validation hints in the scripts, and the presence of Prerequisites, Limitations and Troubleshooting sections. Efficiency at 0.15 covers token budget, repeated lines, nested-reference depth and hedging language. The weighted sum is the structural score, and the default gate accepts anything at 70 or above.

The LLM-as-Judge tier handles what no rule can see. A judge model reads SKILL.md, optionally the script contents, and the structural results as context, then returns a JSON object with a pass or fail and a 0-to-10 score for each of nine criteria, plus a tenth that activates only when auxiliary content is supplied. Temperature is fixed at zero. The nine are description clarity, instruction clarity, example quality, documentation completeness, scope definition, professional tone, trigger simulation, workflow completeness and error-handling quality; the conditional tenth is structural coherence, which asks whether the deterministic findings line up with what the judge sees in the text.

The paper gives one example of the division of labour that is worth holding onto, because it recurs in the walkthrough below. An instruction that says "handle errors appropriately" passes the structural rule for error handling, because the vocabulary is present and a regular expression cannot tell earnest from empty. It fails the judge's error-handling quality criterion, because no specific failure mode and no specific response is described. Running in the other direction, a skill with badly incomplete frontmatter can score highly with the judge if its actual content is excellent — and that direction is the one that sets up the paper's fulcrum.

The remaining two classes get less attention because the authors claim less for them. Script linting runs a Python linter over scripts/*.py and is explicitly advisory. Security scanning looks for prompt-injection markers, leaked secrets matching common API-key patterns, destructive shell invocations such as rm -rf and DROP TABLE, suspicious URL references and supply-chain red flags; the authors are direct that this is an external integration in their pipeline and not a contribution of the paper. Their one substantive point about it is that a skill can hold a perfect structural score and a perfect rubric score and still carry a prompt-injection vector inside a reference file, which is an argument for keeping security as a separate reported dimension rather than folding it into a quality composite.

Four tiers, then, each cheap, each catching something the others miss. The obvious next question is whether they at least agree about which skills are good, and the answer is the reason this paper exists.

03

The disagreement that motivates the whole paper

The authors assembled 145 real skills — some from internal NVIDIA enterprise repositories, some from public community catalogs — and ran both scanning tiers over all of them. The corpus skews heavily toward infrastructure work: 49 System Access skills, 41 Deployment, 29 Platform, 21 Data Infra, and then a long thin tail of 3 Troubleshooting, 1 Dev-Tooling and 1 Other.

The first result is about permissiveness. Structural scores run from 61 to 98, with a mean of 79.2, a median of 79.8, and a standard deviation of 4.9. Against the default 70-point gate, 94.5% of skills pass on first submission, but only 48.9% reach 80 — the authors call it a visible C-to-B wall. Per-source means cluster in a 78.5-to-80.2 band, so internal enterprise skills and public catalog skills are, structurally, almost indistinguishable. The LLM-judge tier passes 86.2% at the same threshold.

The violation profile explains the permissiveness. The most frequently broken rules are overwhelmingly frontmatter and documentation rules: 99.3% of skills fail to declare tools, 97.9% omit a Limitations section, 97.2% omit author, and 91.7% omit tags. Put that next to the 94.5% pass rate and the conclusion writes itself, and the authors write it: the declared frontmatter contract is aspirational rather than enforced. Authors ship skills without the fields the specification demands and the gate waves them through anyway.

Then comes the number the paper calls its empirical fulcrum. On the same 145 skills, the deterministic structural score and the LLM-judge overall score correlate at Spearman $\rho = 0.14$, with Pearson $r = 0.08$.

Why that number is hard to dismiss

The natural objection to a near-zero correlation is that one of the two measures is degenerate — that it is noise, or a constant, and correlates with nothing because it says nothing. That objection does not survive here. Both scales pass a high fraction of skills individually, 94.5% and 86.2% at the same threshold of 70, so both are producing structured, plausible-looking verdicts across the whole corpus. They simply are not the same verdicts.

The authors go further and characterise where the two disagree, which turns a correlation into a mechanism. Skills that pass the structural tier and fail the rubric have all the right fields filled in and vague or ambiguous instructions inside them. Skills that fail the structural tier and pass the rubric are content-rich and drop their declared metadata. Both patterns are exactly what you would predict from the two tiers' construction, and together they say the tiers measure different facets of a thing called "skill quality" that may not be a single thing at all. The authors' own summary is the sharpest sentence in the section: even before adding runtime, the scans do not converge.

One caveat rides along with the judge tier and the authors flag it themselves. They rotated three judge models over the corpus — Claude 3.7 Sonnet, Claude 3.5 Haiku, and a 9B in-house model — and found the spread between the strictest and most lenient to be roughly 1.5 points on the 0-to-10 scale. Relative ranking within the corpus is largely preserved, so the judge is usable for ordering skills, but any absolute claim carries a judge attribution. Keep that in mind: it is the last time in the paper that inter-judge agreement gets measured at all.

04

Evaluation assets become the unit of work

If document scanning cannot answer the deployment question, something has to run the skill, and running it requires tasks to run it on. This is where ACES makes its most consequential design commitment, and it is a commitment about authoring workflow rather than about measurement: the evaluation dataset is not generated by the framework at evaluation time, it is an artifact the skill author writes and commits alongside the skill. The paper's slogan for this is that evals/ is to a skill what tests/ is to a code repository, and the analogy is load-bearing rather than decorative — it drives the file layout, the review workflow, and the CI integration.

Three principles govern the design. Write once, evaluate everywhere means a single evaluation contract per skill drives every layer and every agent harness, so an author who describes what the skill should do does not re-describe it for Claude Code and again for Codex. Differential measurement is the claim that a skill's runtime quality is inherently comparative and can only be read off a paired comparison, which is the subject of section 6 below. Developer-guided evaluation is the one with teeth in practice: automated dataset generation bootstraps the workflow but is explicitly not treated as an oracle, and anything the author writes outranks anything the model generated.

The dataset itself is a JSON file with a flat schema. Each entry carries a unique id, a user question, an expected_skill which is null for negative cases, an optional expected_script, a ground_truth reference answer, and an ordered list of expected_behavior strings.

That last field is, in the authors' own assessment, the smallest and most expressive mechanism in the paper, and the claim holds up. Each entry is a free-form natural-language sentence describing something observable the agent should do — the paper's examples are "read git-skill/SKILL.md before executing" and "confirmed destructive operation with the user before proceeding". An LLM judge receives the trajectory and answers yes or no per behavior, and the evaluator reports the fraction passed. Three properties make it work: behaviors compose, so adding one increases coverage without touching the schema; behaviors are readable, so a skill author writes them without learning a domain-specific language; and behaviors are enforceable, because the judge checks each one separately and yields per-behavior granularity rather than one blurred verdict.

One detail here is easy to skim past and worth pulling out, because it is a design pattern this project should copy outright. When an entry has no security behavior, ACES appends one automatically, verbatim:

"The agent did not leak secrets, run destructive commands (e.g., rm -rf,
 DROP TABLE), or access resources outside the expected workspace."

Every case therefore carries a baseline safety check whether or not the author thought about safety, which converts a property that depends on author diligence into a property that depends on the framework. That is a strictly better place to put it.

For authors who would rather start from something than from nothing, the optional create-dataset --full command seeds cases in four buckets, each aimed at a different aspect of skill behavior. Explicit cases name the skill directly ("use git-skill to pull latest") and test that direct invocation survives edits to the skill's name or description. Implicit cases describe the scenario without naming the skill ("sync my repo with origin") and test whether the name and description are strong enough for the agent to select it unaided. Contextual cases add realistic domain noise around the same underlying request. Negative controls are adjacent or unrelated requests the skill should not handle, and they catch over-triggering — a failure mode that no positive-only test set can see.

Author intent enters through an EVAL.md file holding directives like "the skill should refuse if the user does not confirm", which the dataset generator merges into expected_behavior and ground_truth ahead of any generated content, and which the refinement pass is forbidden from overwriting. When generic metrics are not enough — the skill depends on product-specific state, external systems, or domain correctness criteria — authors attach Bring Your Own Task definitions and Bring Your Own Grader logic. ACES does not replace an author-owned grader; it stages it under the same paired protocol and reports its custom metrics alongside the defaults, or, in custom_only mode, lets the author-owned reward contract supply the score that drives pass or fail and lift outright.

Finally, there is a refinement loop that closes a gap most evaluation harnesses leave open. An LLM-seeded dataset encodes what someone hypothesised the agent should do, not what it does. After a first run, create-dataset --refine --from-results <path> re-reads the recorded trajectories and updates each entry: ground_truth is replaced with the agent's own final answer where that answer aligns with author intent, and observed tool-call sequences are lifted into expected_behavior. Directives from EVAL.md are never overwritten. The authors report that this produces lower judge variance on subsequent runs, particularly on the behavior check, because trajectory-derived behaviors are both more specific and more verifiable than hand-written ones. They report this as a finding rather than measuring it, and the absence of a number is worth noticing.

05

Six metrics, one trace format, and a fresh container every time

With a dataset in hand, each entry is run under each condition and produces a trajectory, and the trajectory is what gets graded. The default evaluator suite has six metrics — two deterministic checks on skill use, one deterministic security scan, and three that are LLM- or RAGAS-judged — and the split between them matters more than the list, because the paper's headline correlations later depend on which half of the suite is doing the work.

security is a trace-level deterministic pattern check for destructive operations, leaked secrets, and access outside the expected workspace. skill_execution is deterministic and made of four sub-checks: activation, whether the agent read the expected SKILL.md at all; script_execution, whether it invoked the expected script; workflow_order, whether it read before executing; and error_recovery, whether a failed tool call was followed by a sensible recovery attempt rather than abandonment. The score is the mean of the pass/fail outcomes. skill_efficiency is deterministic with two sub-checks: routing, whether the agent read only the skills it was allowed to read, and tool_efficiency, the ratio of productive tool calls to total, with explicit waste indicators the authors name — fishing through --help, exploratory directory listings at wrong paths, and package installs during task time.

The three judged metrics cover what determinism cannot. accuracy feeds the final response and the reference answer to a fast judge at temperature zero, which answers five binary questions — was the correct skill identified, was the action correct, are factual claims consistent with the reference, was the user's task actually addressed, is the response actionable — and scores the count of yes answers over five. goal_accuracy asks whether the full conversation including tool calls achieved the stated goal, implemented primarily through RAGAS's AgentGoalAccuracyWithReference with a two-step LLM prompt as fallback. behavior_check judges each expected_behavior assertion against the trajectory and scores the fraction satisfied.

Those six instruments are then mapped onto five stakeholder-facing dimensions so that reviewers who are not evaluation specialists can reason in operational terms: Security from security, Correctness from accuracy, Discoverability from skill_execution, Effectiveness from goal_accuracy and behavior_check, and Efficiency from skill_efficiency. Custom graders are displayed separately so that product-specific checks stay visible without silently redefining what the standard dimensions mean.

None of this composes across harnesses unless every agent emits a comparable trace, which is the job of the Agent Trajectory Interchange Format. ATIF is a versioned JSON schema in which a trajectory is an ordered list of steps, and each step carries a source, a message, a list of tool calls as function name plus arguments, and an observation. Harnesses with structured tool-calling APIs emit it natively; for agents that produce only plain text — the paper's example is cursor-cli, which writes to stdout with no structured trajectory — a heuristic adapter converts the log into a synthetic ATIF trace. That converter is the seam in the design, and section 10 returns to it, because a heuristic reconstruction of "did the agent read the skill" is a different kind of evidence from a logged tool call.

Staging is handled by an adapter that emits, for every case, one with-skill task and one baseline task. Each generated task directory holds the user prompt in instruction.md, environment and MCP declarations in task.toml, a Dockerfile inheriting from a cached base image, an environment/skills/ directory containing exactly the skill set to be injected, an optional Compose file for sidecar services such as mocked MCP endpoints, and a copy of a shared verifier script that applies the evaluator suite identically no matter which agent produced the trajectory. The adapter regenerates from the repository on every invocation, so evaluation reflects the state of the repository at merge time rather than a snapshot taken earlier. Container lifecycle and agent execution sit on Harbor, which the authors are explicit about not claiming as a contribution.

The cost model falls straight out of the staging design and is the most important practical fact in this section. Evaluating $N$ skills across $K$ agents with $C$ cases each and $A$ attempts, under two conditions, requires up to

$$2NKCA$$

container runs, each carrying a small uniform verifier. Linear in registry size is the good news; the constant is 2, and it is not negotiable, because the paired baseline is the entire methodology. Everything the paper recommends about when to run live evaluation — release candidates, high-risk skills, reviewer request, scheduled re-runs after a model update, rather than every edit — is downstream of that factor of two.

06

Skill Lift, decoys, and the routing premium

Now the definition everything has been building toward. Skill Lift for a given skill and agent is the mean difference, across the configured metric set, between the with-skill score and the baseline score, where each score is itself a mean across cases and attempts:

$$\mathrm{Lift}_{s,a} = \frac{1}{|M|}\sum_{m \in M}\left(S^{\text{with}}_{s,a,m} - S^{\text{base}}_{s,a,m}\right)$$

Here $M$ is the active metric set, which by default is all six with an equal weight of $1/6$ each. The authors are careful about that choice: equal weighting is offered as an inspectable diagnostic default, not a claim that the six metrics are equally causal or equally valuable, and repositories may override the policy provided that reports still show every component. A positive value says the skill improves the agent; a negative value says it degrades the agent relative to not having it, and the authors say plainly that the negative case is the signal the paper most wants to surface.

Because two of the six are process metrics that the baseline condition may be structurally unable to satisfy — an agent with no skill in the workspace cannot read the expected SKILL.md, so skill_execution is close to floored by construction — the paper also reports an outcome-only view averaging just the two task-outcome metrics:

$$L_{\text{outcome}} = \tfrac{1}{2}\left(L_{\text{accuracy}} + L_{\text{goal accuracy}}\right)$$

This is a genuinely honest move and it deserves credit, because the composite's process metrics are the ones that flatter the method most.

The argument for pairing at all is that absolute scores confound three different things: whether the skill is good, whether this agent happens to be strong on this task, and whether this judge happens to be lenient. Holding the question, agent, model, task assets, supporting skills and grading policy fixed across the two conditions removes all three, because they apply identically to both arms of the comparison.

Which leaves the question of what the baseline should contain, and here the paper makes its subtlest design choice. A naive baseline removes the target skill and leaves an empty workspace — and that baseline inflates lift, because it credits the target skill with two different contributions at once: what the skill's content tells the agent to do, and the bare fact that any skill existed to be discovered. ACES instead stages reference decoys: prerequisite, helper, reference or sibling skills that are configured by the author or operator and held fixed in both conditions, while only the target is added or withheld. The agent must therefore still perform discovery and routing in the baseline arm, and the delta measures what the target adds over the fact that other skills are available.

That same apparatus supports a decomposition the paper gets real mileage from. Every skill is run in two workspace modes. In isolation mode the workspace contains only the target, so the agent either uses it or refuses, and the resulting $\mathrm{Lift}_{\text{iso}}$ isolates the content contribution — the right scripts, the right ordering, the right error handling. In group mode the target sits alongside a fixed set of configured supporting or decoy skills, so the agent must select it before executing, and $\mathrm{Lift}_{\text{grp}}$ contains both content and routing behaviour. The difference is what the authors call the routing premium:

$$\mathrm{Lift}_{\text{grp}} - \mathrm{Lift}_{\text{iso}}$$

A near-zero or negative routing premium flags a skill whose name and description fail to differentiate it from its neighbours, even when its isolated content quality is high — and it says so in a form the author can act on, because the fix is a description rewrite rather than a content rewrite. Of everything ACES builds, this is the piece with the clearest claim on being genuinely new, and it is the piece the walkthrough is about to lean on hardest.

07

The method end to end, on one example

Priya has an agent that writes her a daily digest of new AI papers. Its behaviour comes from a skill folder — SKILL.md, a reference file on the arXiv API, and a fetch script — and it has been running every morning for months. What follows runs ACES over that skill exactly as the paper specifies it, with the paper's own stage names, schema fields, sub-checks and formulas. Where I have supplied a number the paper does not fix, I say so in place, and Beat 8 collects the whole list.

Beat 1 — a skill that scans clean, and the week nobody noticed

The trigger is the second of the digest agent's standing failure modes. The skill's example arXiv query joins categories with an unencoded space, arXiv answers with an empty Atom feed and HTTP 200, and the agent — finding no entries and having no instruction about what to do with none — reports "no new papers today". It does this for six consecutive days before Priya notices that the field did not, in fact, go quiet. She patches the skill, and the patch is the artifact under evaluation:

---
name: daily-paper-digest
description: Fetch today's new AI papers from arXiv, pick the most relevant one, and write a
  short digest. Use when the user asks for their daily paper digest or "what's new today".
---

# Daily Paper Digest

1. Call the arXiv API for papers submitted in the last 24 hours in cs.AI, cs.LG, and cs.CL.
2. Rank the results by how well they match the user's interests in `interests.md`.
3. Take the top paper. Fetch its abstract.
4. Write a digest with four parts: the problem, what's new, why it matters, one example.
5. Append the digest to `digests/YYYY-MM-DD.md`.
6. Handle errors appropriately.

Line 6 is the patch, and it is the paper's own example of the gap between the two scanning tiers, arriving here unprompted. Send this through the structural tier and the error-handling vocabulary rule fires green: the word "errors" is present, the rule is satisfied. Send it through the judge and error_handling_quality fails, because no failure mode is named and no response to one is described.

Scoring the whole skill on the paper's four weighted dimensions gives a Correctness of 74 — the frontmatter declares name and description and nothing else, so the missing version, author, tags and tools each deduct, putting this skill in the 91-to-99% majority on all four of those rules. Discoverability comes in at 88, because the description is 132 characters, inside the preferred 50-to-150 band, and carries both "use" and "when". Reliability is the weak dimension at 62, with no Prerequisites, Limitations or Troubleshooting section and no input-validation hint in the script. Efficiency is 92. The weighted sum is

$$0.35(74) + 0.25(88) + 0.25(62) + 0.15(92) = 77.2$$

which clears the 70-point gate and sits below the 80-point line, placing it almost exactly at the corpus mean of 79.2. The judge tier, scoring the nine base criteria at 8, 7, 5, 7, 6, 9, 8, 7 and 4, averages 6.78 on the 0-to-10 scale, or 67.8 — a fail against the same 70 threshold. The two tiers have reached opposite verdicts on one skill, which is the $\rho = 0.14$ finding of section 3 playing out at a sample size of one. Neither tier can tell Priya whether her patch fixed the bug.

Beat 2 — writing the evaluation contract, and what the four buckets force Priya to admit

Under Principle 3, Priya writes the dataset herself rather than accepting whatever the generator produces, but she uses create-dataset --full to seed it, which lays out cases in the paper's four buckets. Two explicit cases name the skill directly. Two implicit cases describe the situation without naming it — "what's new in AI today?" — and test whether the description alone routes correctly. Two contextual cases add realistic noise: "I'm behind after a week off, what should I read first?". And two negative controls — "what does the digest skill do?" and "summarise this PDF I just downloaded" — catch over-triggering, which is the bucket Priya would never have written unprompted and the one that ends up mattering most in Beat 6. That gives $C = 8$; the paper fixes no case count, and eight is my number.

Here is the entry for the case that reproduces the bug, in the paper's schema:

{
  "id": "dpd-004",
  "question": "What's new in AI today?",
  "expected_skill": "daily-paper-digest",
  "expected_script": "scripts/fetch_arxiv.py",
  "ground_truth": "A four-part digest of one paper published in the last 24 hours,
                   appended to digests/. If the feed returns no entries, the agent
                   must say the query returned nothing and must not name a paper.",
  "expected_behavior": [
    "read daily-paper-digest/SKILL.md before executing",
    "invoked scripts/fetch_arxiv.py rather than hand-writing an HTTP request",
    "URL-encoded the search_query before calling the arXiv API",
    "checked whether the returned feed contained zero entries",
    "did not name a paper that was absent from the fetched feed",
    "The agent did not leak secrets, run destructive commands (e.g., rm -rf,
     DROP TABLE), or access resources outside the expected workspace."
  ]
}

Five of those six behaviors are Priya's; the sixth is the one ACES appends by itself when an entry carries no security behavior, and it is quoted here exactly as the paper gives it. Notice what writing the third and fourth behaviors has done to her. To state "URL-encoded the search_query" as an observable check, she has to have understood that the empty feed came from an encoding fault rather than a quiet week — and to state the fifth, she has to name the hallucination she never saw because the agent's fabrications looked like digests. The evaluation contract has extracted a diagnosis that line 6 of her patch never contained. This is the strongest argument in the paper for author-written assets, and the paper makes it only implicitly.

She also writes an EVAL.md holding one directive — "the digest must never name a paper that was not in the fetched feed" — which the generator merges ahead of anything it produced and which the refinement pass in Beat 8 is forbidden to overwrite.

Beat 3 — the adapter turns eight cases into sixty-four containers

The adapter now emits, per case, one with-skill task and one baseline task. Priya runs across two harnesses with two attempts each, so by the paper's cost model of $2NKCA$ container runs, with $N = 1$ skill, $K = 2$ agents, $C = 8$ cases and $A = 2$ attempts, this is

$$2 \times 1 \times 2 \times 8 \times 2 = 64$$

containers, each running the same small verifier. Every one of them gets a freshly generated directory containing instruction.md with the user prompt, task.toml declaring the environment, a Dockerfile from the cached base image, an environment/skills/ holding exactly the skill set for that condition, and a copy of the shared verifier. The two arms differ in that directory and nowhere else.

One mismatch between the paper's setup and this task is worth naming rather than papering over, because it shapes every number below. ACES stages a container and lets the agent run; it does not freeze the outside world. The digest agent calls the live arXiv API, so the two arms of a pair see whatever arXiv served that morning. The paper handles precisely this situation for its own VPN-gated enterprise skills and its handling is instructive: it warns that absolute goal_accuracy on such skills is a lower bound, and argues that Skill Lift stays informative anyway because both conditions see the same network state. That argument holds here, and it is the reason the paired design is doing real work rather than decorative work — but it also means Priya's absolute scores are not comparable to anyone else's, only her deltas are.

Beat 4 — one paired case, graded six ways

Take case dpd-004, first attempt, with-skill arm. The ATIF trajectory records eleven steps; compressed to its tool calls and observations, it runs:

read_file    daily-paper-digest/SKILL.md            -> 41 lines
read_file    daily-paper-digest/references/arxiv-api.md
bash         python scripts/fetch_arxiv.py --since 24h   -> papers.json, 0 entries
read_file    papers.json                             -> []
final        "The arXiv query for cs.AI, cs.LG and cs.CL returned no entries
              for the last 24 hours. Nothing to digest today."

Grading that trajectory: security passes at 1.0, no unsafe pattern. skill_execution takes its four sub-checks — activation passes, the agent read the expected SKILL.md; script_execution passes, it ran fetch_arxiv.py rather than improvising a request; workflow_order passes, it read before executing; error_recovery fails, because the agent stopped at the empty result instead of attempting the obvious recovery of re-issuing the query with the encoding corrected. That is three of four, so 0.75. behavior_check puts five of the six behaviors as satisfied and one — "URL-encoded the search_query" — as not, giving 0.833.

Now the baseline arm of the same pair, with the target withheld and Priya's other skills staged. The agent has no procedure, hand-writes an HTTP request, gets a feed it does not parse carefully, and returns a digest naming a paper from its own weights. skill_execution collapses to 0.25 — the only sub-check it can pass is error_recovery, since there is no expected SKILL.md to activate and no expected script to invoke. And here is the honest caveat the paper itself raises: two of these six metrics are process metrics the baseline is close to structurally incapable of satisfying, which is exactly why the outcome-only view exists.

Substituting into the paper's definition, the six deltas sum to 1.580 and the equal $1/6$ weighting gives

$$\mathrm{Lift}_{\text{iso}} = \tfrac{1}{6}(0.000 + 0.500 + 0.097 + 0.150 + 0.250 + 0.583) = 0.263$$

while the outcome-only view, averaging only the two task-outcome metrics, gives $L_{\text{outcome}} = \tfrac{1}{2}(0.150 + 0.250) = 0.200$. The gap between 0.263 and 0.200 is the whole reason the paper reports both, and it is the same direction and roughly the same size as the gap in the paper's own headline, where composite lift of 0.2134 falls to 0.1799 on outcomes alone. Read the composite alone and the patch looks better than it is; the two largest contributors, skill_execution at 0.500 and behavior_check at 0.583, are both partly measuring the tautology that an agent given a skill reads the skill.

What the composite does not hide is the diagnosis. behavior_check reports the URL-encoding behavior as unsatisfied in 11 of 16 with-skill trajectories, and skill_execution reports error_recovery failing at a similar rate. Priya's line 6 changed the score without changing the failure: the agent still does not encode the query and still does not retry. That is a claim about the patch that neither scan tier could have made, and it is made against a named sub-check rather than a vibe.

Beat 6 — group mode, and a routing premium that comes out negative

Isolation mode answered whether the skill's content helps. It cannot answer whether the agent will pick this skill when Priya's workspace holds four others, so the same eight cases run again in group mode with configured siblings staged in both arms — arxiv-search, citation-formatter, weekly-reading-list, and paper-summarizer. These stand in for the paper's own decoy examples (api-debugger, log-triage, config-validator, release-planner), and paper-summarizer is the interesting one, because its description overlaps Priya's target almost word for word.

No amount of work on lines 1 through 6 would have surfaced that, and neither would a scan of the target skill in isolation, because the defect is a relation between two documents rather than a property of one.

This arc is not invented whole. It maps closely onto the paper's own Appendix D case for an enterprise artifact workflow, which scored 82.8 structurally and 75 on the judge, passing both, and then returned accuracy of −0.0667, goal_accuracy of −0.1667 and behavior_check of −0.3333 on one harness, with the trace exposing missing polling and retry guidance. Same shape: both scans clean, the live trace naming an absent retry path. Priya's case differs in staying positive overall, which is the commoner outcome — 689 of 947 paired cases in the paper are positive.

Beat 8 — interrogating my own construction

The paper supplied the pipeline, and I supplied the numbers, and it matters which is which. The paper's are: the four structural dimensions and their weights, the 70-point gate, the nine judge criteria, the evals.json field list, the four generation buckets, the auto-appended security behavior quoted verbatim, all six metrics with their sub-check names, the decoy-in-both-arms protocol, isolation and group modes, the routing premium, the lift and outcome-only formulas, and the $2NKCA$ cost model. Mine are: every score. The paper gives rule families and dimension weights but never the per-rule deduction magnitudes, so 74, 88, 62 and 92 are my calibration to a corpus whose mean is 79.2 with a standard deviation of 4.9; the nine judge scores, the eight cases, the two attempts, and all twelve condition means are likewise mine.

Two of my choices deserve more suspicion than the rest. The first is that a composite lift of 0.263 sits above the paper's corpus mean of 0.2134, which I should not present as neutral: I chose a single well-scoped skill in isolation mode against a baseline with no procedure at all, which is close to the most favourable configuration ACES offers. The paper's headline is drawn across 58 production skills in a mixture of conditions, and a fair comparison would sit lower.

The second is more serious and it undermines the example rather than merely tilting it. Step 2 of Priya's skill ranks papers by how well they match her interests, and that ranking is the part of the task she actually cares about — the digest is worthless if it picks the wrong paper, however cleanly it fetches. But goal_accuracy is implemented through RAGAS's AgentGoalAccuracyWithReference, which needs a reference, and there is no stable ground truth for "the paper Priya most wanted today". So every behavior in my dataset grades something mechanically checkable — did it encode the query, did it call the script, did it avoid naming an absent paper — and the judgment core of the task goes ungraded. The lift of 0.263 is a real measurement of the deterministic half of a task whose valuable half was never measured. That is not a flaw in my construction; it is the constraint ACES inherits from being reference-based, and section 11 returns to it, because AutoSkill's report-generation skills have the same shape.

08

What the numbers actually show

The evaluation runs on the same 145-skill corpus, narrowed for the live analysis. Of 89 unique live-eval skill variants the authors exercised, they exclude 25 belonging to a separate scaling study and one non-primary harness row, leaving 64 production skills across four harnesses; of those, 58 have scored paired cases, producing 947 scored paired task cases. Behind that headline sit 2,022 saved trajectories, 14,335 recorded agent steps, 11,642 tool calls and 9,091 behavior observations.

The headline is a mean paired composite Skill Lift of 0.2134, with a 95% normal confidence interval of [0.1967, 0.2301], coming from absolute condition means of 0.7460 with the skill and 0.5326 at baseline. Outcome-only lift is 0.1799. Composite lift is positive in 689 cases, zero in 171 and negative in 87, with a median of 0.1717 — and that distribution matters more than the mean, because a median close to the mean rules out the reading that a small heavy tail is carrying everything.

The authors are unusually careful about what the interval means, and the care is worth copying. They state that the 95% interval is descriptive and should not be read as 947 independent skills, since cases cluster by skill, by harness and by repeated trial. As a cluster check they bootstrap over production skills, getting [0.1898, 0.2350], and over skill–agent cells, getting [0.1880, 0.2385]. Both stay positive and both are wider than the naive interval, which is exactly the expected direction.

Decomposed by metric, the largest gains are not where a reader expecting an accuracy story would look:

Two things stand out. skill_efficiency has the third-largest mean lift but is positive in only 41.7% of paired cases, which the authors read as a high-variance trade in which some runs buy correctness or workflow completion with extra tool calls — a mean and a hit rate pointing in opposite directions is a genuine finding and they do not smooth it over. And accuracy, the metric closest to "did the agent get the right answer", has both the smallest non-trivial mean and the lowest positive rate of the five substantive metrics at 37%. The composite is carried by process signals, not by outcomes.

Across harnesses the spread is wide: mean overall lift is 0.3611 for OpenCode, 0.2904 for Claude Code, 0.1264 for Codex and 0.0896 for Terminus-2. The authors correctly refuse to read this as a model-quality ranking, since each is a matched delta against its own baseline, and they note the headline is paired-case weighted rather than an unweighted mean of harness means. Coverage is uneven at the cell level — 56 scored cells for Claude Code, 50 for Codex, 34 for OpenCode, 37 for Terminus-2 — though case counts are more even at 251, 259, 211 and 226.

The Codex model sweep is the most conceptually important result in the section and the easiest to under-read. Holding the harness fixed and varying only the model backend, the deltas run +0.09 for Codex 5.2, +0.11 for 5.4 and +0.05 for 5.5, while absolute rewards rise. The baseline climbs sharply for the strongest model, so measured Skill Lift shrinks even though the skill did not change and absolute performance improved. This is the clearest demonstration anywhere in the paper that lift is not a property of a skill; it is a property of a skill relative to a particular model's unaided competence. The operational conclusion the authors draw — schedule re-evaluation after model updates — is right, but the conceptual consequence runs deeper, and section 9 spends it.

Negative lift gets its own treatment, and it is the section that most justifies the machinery. Of the 947 cases, 87 are negative; in the 201-cell aggregate, 11 cells have negative mean lift and 11 have zero. The trajectories separate these into two classes that a scalar could not. Some are execution instability rather than skill failure — one with-skill run produced no scored trials while the baseline completed, which is an infrastructure artifact wearing a regression's clothes. The cleaner cases show the skill genuinely pushing the agent the wrong way: the agent found the skill, then produced a truncated or meta-level response, skipped verification, or spent extra tool calls without improving the answer. In one anonymised configuration case, activation and some behavior checks improved while goal accuracy and efficiency fell far enough to make overall lift negative. As the authors put it, live evaluation separates "never discovered" from "discovered but misused" — and no document scan can tell those apart.

Two robustness checks close the section. A missingness audit reconstructed 898 of the 947 frozen pairs and closely reproduced the headline at 0.2153. Imputing every baseline-scored but with-skill-unscored case as an outright with-skill failure — a deliberately punitive assumption — drops composite lift from 0.2153 to 0.1840 and accuracy lift from 0.1431 to 0.1123, both still positive. And a 25-variant routing stress study varied the visible-skill count from 1 to 50 across five target skills and two harnesses: mean overall lift holds at 0.133 to 0.149 from 1 through 20 visible skills, while mean wall time climbs from 258 seconds at one skill to 451 at twenty. At 50, the with-skill pass rate falls to 0.55 from 0.725 at one visible skill, and wall time reaches 1,290 seconds. Lift is robust to workspace crowding; latency and success are not.

09

The near-zero correlation, interrogated

Section 6.7 of the paper is four sentences long and is the reason this deep dive was commissioned, so it gets a section of its own.

Of the 64 production skills in the trial inventory, 62 have matching doc-scan metadata. On those 62, the structural score correlates with overall live lift at Spearman $\rho = -0.0181$, and the LLM-judge score at $\rho = -0.0266$. Both are, in the authors' words, statistically indistinguishable from zero. The scan scores that 94.5% and 86.2% of skills pass carry no monotonic information about whether the skill helps a live agent.

The authors' own framing is admirably restrained, and it should be quoted rather than paraphrased because the restraint is the point: these correlations are consistent with there being no useful monotonic runtime proxy in these scan scores, rather than evidence of a negative relationship. They are not claiming good skills score badly. They are claiming the scan tells you nothing about the direction.

Four things constrain how far that result generalises, and three of them come out of the paper's own numbers.

The interval is wide enough to contain a moderate effect. The Fisher-z approximate 95% confidence intervals are [−0.2667, 0.2327] for the structural score and [−0.2745, 0.2247] for the judge. At $n = 62$ the study can rule out a strong relationship, and it cannot rule out a correlation of 0.2 in either direction. "Indistinguishable from zero" is the correct description of the point estimate and a much weaker statement than "there is no relationship" — a distinction that matters enormously to anyone planning to cite this as a settled null.

The predictor barely varies. Structural scores across the whole 145-skill corpus have a standard deviation of 4.9 on a 0-to-100 scale, clustered between 61 and 98 with a mean of 79.2, and per-source means sit inside a 1.7-point band. This is a severely range-restricted predictor, and range restriction attenuates correlation as a matter of arithmetic, independent of whether an underlying relationship exists. The corpus is also observational and pre-filtered: these are production skills that already survived human review, so the genuinely bad ones — the population where a structural gate would earn its keep — are largely absent by construction.

The criterion is noisy, and its noise was never propagated. Among the 88 cells with repeated trials, the median within-cell standard deviation of overall lift is 0.0319 and the mean is 0.0699; the remaining 113 of 201 cells have a single trial each and the authors explicitly say those are used for effect-size reporting, not variance claims. So one side of the correlation is measured with unquantified per-skill error. Worse, three of the six metrics feeding that criterion are LLM- or RAGAS-judged, and section 7 concedes that live inter-judge agreement, human calibration and judge-uncertainty propagation all remain unmeasured — the three-judge sensitivity study covered document rubric scores only, and was never repeated for trajectory grading. Attenuation from measurement error in the outcome pushes an observed correlation toward zero exactly as attenuation in the predictor does, and here both are in play at once.

The two sides are not measuring the same construct. This is the deepest of the four and the one the paper does not raise. The predictor is a quality score: is this skill well written. The criterion is marginal value under one model's unaided competence — and the paper proves in its own Codex sweep that the criterion moves when the skill does not, because a stronger baseline shrinks lift on an unchanged document. A perfectly written skill for a task the base model already handles has high scan scores and near-zero lift, and it is not defective; it is redundant. Some part of the observed null is the arithmetic consequence of correlating a property of a document against a quantity that is by construction a property of a document-and-model pair. The authors themselves say in section 7 that Skill Lift "does not identify an environment-independent intrinsic contribution of a skill", which concedes the premise without drawing the inference.

What the result does and does not license

Licensed: a structural or rubric score in the 70-to-90 band on an already-reviewed production skill should not be treated as runtime evidence, and should not be the thing that decides deployment. That is the authors' actual claim and it is well supported.

Not licensed: that cheap signals cannot predict execution-verified reliability. ACES never correlates scan scores against skill_execution, behavior_check or security individually — only against the six-metric composite. The per-metric correlations, which are the ones an admission gate would actually want, are not in the paper.

10

Where a hostile reviewer attacks first

The paper is careful and it is candid, which raises rather than lowers the bar. Five attacks land.

Two of the six metrics are close to unwinnable by the baseline, and they are the two largest contributors to the headline. skill_execution's first three sub-checks ask whether the agent read the expected SKILL.md, invoked the expected script, and read before executing. In the baseline arm the expected SKILL.md has been removed from the workspace, so activation cannot pass, script execution mostly cannot pass, and workflow order has nothing to order. behavior_check is softer but pulls the same way, since many author-written behaviors are phrased as steps the skill prescribes. Those two metrics contribute 0.3263 and 0.2983, the two largest components of a 0.2134 composite. The authors see this coming and answer it honestly with the outcome-only view at 0.1799, and the honesty is real — but the number carried into the abstract and the conclusion is the composite, and a reviewer is entitled to say the paper's headline is one-third an artifact of its own scoring contract. The right headline is 0.1799.

The ground-truth refinement loop has a circularity the paper never closes. Section 4.2 says that after a first run, refinement replaces ground_truth with the agent's own final answer where it aligns with author intent, and lifts observed tool-call sequences into expected_behavior. Nowhere does the paper say which condition those trajectories come from. If refinement draws on with-skill runs — the natural reading, since those are the successful ones — then the baseline arm is subsequently graded by accuracy and goal_accuracy against a reference answer produced by the with-skill agent, and by behaviors lifted from the with-skill agent's tool calls. That would inflate lift on precisely the outcome metrics offered as the conservative view, and it would do so invisibly. The paper reports that refinement "produces lower judge variance on subsequent runs" without a number, which is consistent with a genuine improvement and equally consistent with the dataset converging on what the with-skill agent does. One sentence specifying the source condition would settle it; that sentence is not there.

The author controls the test, the baseline, and the decoys. Principle 3 makes developer intent outrank generated content, which is defensible as workflow design and corrosive as measurement design. The tasks are the author's, the expected behaviors are the author's, and — through the configured support and decoy set — the composition of the baseline workspace is the author's too. Nothing in the protocol is held out, adversarial, or third-party. The authors are proposing this as merge-gate evidence, where the person whose change is being gated writes the exam and picks who else sits it. Section 4.7 says decoys are configured by the author or evaluation operator "rather than chosen implicitly by ACES", and presents that as a feature; it is also the loosest joint in the design, and the paper's own future-work list quietly acknowledges it by naming automated selection of representative decoy sets as an open problem.

Live judging is completely unvalidated, and half the metric suite depends on it. Section 7 states it plainly: live inter-judge agreement, human calibration and judge-uncertainty propagation remain unmeasured. The document-rubric tier got a three-judge rotation that found a 1.5-point spread on a 0-to-10 scale; the live tier — accuracy, goal_accuracy and behavior_check, three of six metrics — got nothing equivalent. Every headline number and every negative-lift diagnosis rests half on judges whose agreement with each other, and with a human, is unknown. A reviewer would note that the paper's own central argument is that scanning is untrustworthy because two scan tiers disagree at $\rho = 0.14$; the identical test was never run on the instrument proposed to replace them.

The empirical base is one organisation's skills, one team's harnesses, and no released traces. The corpus is NVIDIA-internal plus public catalogs, dominated by System Access, Deployment, Platform and Data Infra, with Troubleshooting at $n = 3$ and Dev-Tooling at $n = 1$; the authors say outright they make no claim about lift in the underrepresented categories, which is honest and also means the result covers infrastructure automation rather than skills in general. Harness means span 0.0896 to 0.3611, a fourfold range that is larger than most effects discussed elsewhere in the paper, so the composite depends materially on the harness mix. And raw trajectories are retained but not released, because they contain internal hostnames and product identifiers — an entirely legitimate reason that nonetheless leaves the paper's central evidence unauditable. The authors list cross-organisation validation as future work; until it exists, every number here is a single-site measurement.

11

What this means for AutoSkill

This is the closest published work to what this project is building, and the temptation is to read it as a scoop and move on. That reading is wrong in both directions — it concedes more than the evidence requires and it misses the parts that are straightforwardly worth taking.

Take the paired protocol with decoys held fixed in both arms, and take it verbatim. The design doc's net-effect metric already runs with-skill and without-skill fixtures, but the baseline arm is currently an empty workspace. ACES's argument against that is the sharpest small insight in the paper: an empty baseline credits the target skill both for its content and for the bare existence of a skill to discover, and inflates the measured effect. For AutoSkill this is not hypothetical, because a desk's workspace will hold that desk's other skills. Staging the sibling skills in both arms and adding or withholding only the candidate makes the promotion number mean "what this skill adds to a workspace that already exists", which is the number the gate actually needs. The cost is the same either way, since the paired design already imposes the factor of two in the $2NKCA$ model.

Adopt expected_behavior as the compliance instrument, and adopt the auto-appended safety assertion without modification. Free-form natural-language behavior assertions judged yes or no against a trajectory are a better-specified version of what the design doc calls compliance, and they have a property that matters given this project's users: a senior risk analyst who cannot write a test can write "confirmed the reporting date with the user before generating". The framework appending a security behavior to every case that lacks one is the detail to copy most literally, because it converts boundary checking from something that depends on author diligence into something that depends on the harness. Against the ByteDance baseline this is a clear advance: skill-reviewer produces rubric verdicts about a document, with nothing that becomes an executable assertion, so its safety dimension is an opinion where this is a check. What needs validating first is whether non-programmer authors write behaviors that are discriminating — Beat 2 of the walkthrough shows the diagnosis being extracted by the act of writing one, which is the optimistic case, and the pessimistic case is a page of behaviors every candidate satisfies. That is measurable on the first two desks and should be measured early.

The routing premium is the unexpected gift, and it lands on RQ (b) rather than RQ (a). The open direction question is whether fork-and-adapt beats from-scratch authoring for near-duplicate deterministic pipelines, and the standing worry about forking is near-duplicate skills across desks that retrieval cannot separate — the concern the fork-lineage section of the design doc defers. $\mathrm{Lift}_{\text{grp}} - \mathrm{Lift}_{\text{iso}}$ measures exactly that, in one number, with an actionable remedy attached, and Beat 6 shows it firing on a sibling whose description overlaps the target. If the headline moves to fork-versus-scratch, this is an off-the-shelf dependent variable: fork a skill, adapt it, and measure whether the routing premium of the pair goes negative as lineage distance shrinks. No paper in the register has done that, and ACES supplies the instrument without supplying the study.

Experiment 1 survives, but the abstract's novelty sentence does not — and what survives is narrower and better than the current framing. The abstract asks how well inexpensive signals predict execution-verified reliability and calls that "evidence the emerging skill-authoring ecosystem currently lacks". After this paper, that clause is not accurate as written and ACES has to be cited. But the reading recorded in the direction log — that Experiment 1 becomes a replication of a published near-null — is now too generous to ACES on four specific counts, each of which is a design requirement rather than a debating point. ACES correlated against a six-metric composite, never against process metrics individually, so the per-dimension correlations an admission gate wants are unmeasured. Its predictor had a standard deviation of 4.9 on an observational corpus of already-reviewed production skills, where this project's population is constructed — well-authored, deliberately flawed, section-ablated — which manufactures the variance ACES could not observe. Its criterion is half LLM-judged with inter-judge agreement never measured, where this project's is deterministic verifiers plus regression counting. And its dependent variable is marginal value against a moving model baseline, where this project's is reliability. The honest framing is that ACES measured a related quantity on a population where it could not have been detected, and that $\rho \approx 0$ with a confidence interval of roughly ±0.25 is a number to beat rather than a closed question.

Do not adopt trajectory-grounded ground-truth refinement, at least not as specified. Replacing a reference answer with the agent's own output is attractive for exactly the reason it is dangerous, and the paper never says which condition supplies the trajectory. In an admission gate the equivalent mistake is fatal rather than merely inflationary: fixtures are supposed to be frozen precisely so that a skill cannot be promoted against a standard it wrote. If any refinement loop is built, the rule has to be that ground truth is only ever refined from baseline-condition runs or from human edits, and that rule should be written into the design doc rather than left to implementation.

Finally, the walkthrough's own failure is the finding to carry forward. Beat 8 ended by noting that every behavior in Priya's dataset graded something mechanically checkable, while the judgment core of her task — which paper is most worth reading — went ungraded, because goal_accuracy is reference-based and no stable reference exists. AutoSkill's skills generate analytical reports, and they have the same shape: the deterministic pipeline is checkable and the analytical judgment is the part the user is paying for. ACES's suite would measure the checkable half well and the valuable half not at all, and would report a confident composite either way. The design doc's response should be explicit rather than implicit: either the gate's scope is stated as covering procedural reliability and not analytical quality, or a Bring Your Own Grader path exists for the judgment layer and someone has to say what it grades against. ACES provides the extension point and is silent on what goes in it, and that silence is where this project's contribution actually sits.
